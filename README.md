# dbt Full Demo

A working demo of a Snowflake + dbt pipeline pattern: synthetic provider data in a raw database, zero-copy schema clones for dev/test isolation, incremental dbt models, a Snowflake Dynamic Table, and a daily task pipeline that keeps clones fresh.

---

## Architecture

### High-Level Overview

```
┌─ DATA SOURCE ───────────────────────────────────────────────────────┐
│                                                                     │
│  Synthetic provider + vendor data                                   │
│  generated by 01_historical_data_generation.sql                     │
│                                                                     │
│  Tables: PROV, PROV_ADDR, PROV_COMMUNICATION, PROV_TAXONOMY,        │
│          PRV_XREF, PRV_XREF1, VENDOR, VENDOR_ADDRESS,               │
│          VENDOR_PROVIDER_REF, VENDOR_TAXONOMY                       │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
                          │
              seeds PROD_RAW_DB.ORACLE
                          │
             ┌────────────▼─────────────────────┐
             │  PROD_RAW_DB.ORACLE (authoritative)│
             │  + daily incremental inserts       │
             │    via DAILY_DATA_INSERT task       │
             └────────────┬─────────────────────┘
                          │
             DAILY_CLONE_REFRESH task (child)
             re-clones ORACLE schema each day
                    │              │
          zero-copy clone   zero-copy clone
                    │              │
                    ▼              ▼
         ┌──────────────┐  ┌──────────────┐
         │ DEV_RAW_DB   │  │ TEST_RAW_DB  │
         │   .ORACLE    │  │   .ORACLE    │
         └──────────────┘  └──────────────┘
                    │              │
                    └──────┬───────┘
                           │
                     dbt transforms
                           │
                           ▼
            DEV / TEST / PROD_ANALYTICS_DB
              STAGING · INTERMEDIATE · MARTS
```

`PROD_RAW_DB.PUBLIC` holds the tasks and procedures — this schema is intentionally never cloned into DEV/TEST, so the pipeline infrastructure stays in prod only.

### dbt Model Layers

```
┌─ Source Layer  (PROD_RAW_DB / DEV_RAW_DB / TEST_RAW_DB) ──────────────────────┐
│  schema: ORACLE                                                                │
│  PROV, PROV_ADDR, PROV_COMMUNICATION, PROV_TAXONOMY,                           │
│  PRV_XREF, PRV_XREF1, VENDOR, VENDOR_ADDRESS,                                  │
│  VENDOR_PROVIDER_REF, VENDOR_TAXONOMY                                          │
└────────────────────────────────────────────────────────────────────────────────┘
                                        │
                                        ▼
┌─ Staging Layer ────────────────────────────────────────────────────────────────┐
│  materialization: VIEW                                                         │
│  schema: STAGING                                                               │
│                                                                                │
│  stg_oracle__providers          ← PROV                                         │
│  stg_oracle__vendors            ← VENDOR                                       │
│  stg_oracle__vendor_provider_ref← VENDOR_PROVIDER_REF                          │
└────────────────────────────────────────────────────────────────────────────────┘
                                        │
                                        ▼
┌─ Intermediate Layer ───────────────────────────────────────────────────────────┐
│  materialization: TABLE                                                        │
│  schema: INTERMEDIATE                                                          │
│                                                                                │
│  int_provider_addresses         ← joins provider + address data                │
│  int_provider_taxonomy          ← joins provider + taxonomy data               │
│  int_provider_communication     ← joins provider + communication data          │
│  int_provider_xref              ← joins provider cross-reference data          │
└────────────────────────────────────────────────────────────────────────────────┘
                                        │
                                        ▼
┌─ Marts Layer ──────────────────────────────────────────────────────────────────┐
│  schema: MARTS                                                                 │
│                                                                                │

│                                 picks up rows on or after current watermark    │

```

### Daily Task Pipeline

```
8:00 AM MT
     │
     ▼
┌─ DAILY_DATA_INSERT (root task) ────────────────────────────────┐
│  Calls INSERT_INCREMENTAL_DATA()                               │
│  Inserts ~75 providers + 50 vendors + 100 vendor-provider links│
│  into PROD_RAW_DB.ORACLE with LAST_MODIFIED_DATE = today       │
└────────────────────────────────┬───────────────────────────────┘
                                 │ on success
                                 ▼
┌─ DAILY_CLONE_REFRESH (child task) ─────────────────────────────┐
│  Calls REFRESH_DEV_TEST_CLONES()                               │
│  CREATE OR REPLACE SCHEMA DEV_RAW_DB.ORACLE  CLONE PROD        │
│  CREATE OR REPLACE SCHEMA TEST_RAW_DB.ORACLE CLONE PROD        │
│  Re-applies USAGE + SELECT grants to analytics roles           │
└────────────────────────────────────────────────────────────────┘
```

## Quick Reference

| Term | What It Means |
|---|---|
| **PROD_RAW_DB.ORACLE** | Authoritative source data; seeded by script 01, grown daily by task pipeline |
| **PROD_RAW_DB.PUBLIC** | Holds tasks + procedures; never cloned into DEV/TEST |
| **DEV/TEST_RAW_DB.ORACLE** | Zero-copy clones of PROD — production-quality data, no storage cost until diverged |
| **DAILY_DATA_INSERT** | Root task; fires at 8am MT; inserts ~200 records into PROD |
| **DAILY_CLONE_REFRESH** | Child task; fires after insert; re-clones ORACLE schema into DEV and TEST |
| **dim_provider** | Incremental model; merges on provider_id; picks up rows on or after watermark |
| **fct_provider_county_summary** | Snowflake Dynamic Table; 1-hour lag; breaks after re-clone until `--full-refresh` |
| **CHANGE_TRACKING** | Enabled on PROV + VENDOR in all three raw DBs; required by the Dynamic Table |
| **zero-copy clone** | Instant schema copy with no storage cost until data diverges |
| **--full-refresh** | Rebuilds all models from scratch; required in DEV/TEST after each re-clone |

## Setup Walkthrough

### Step 1 — Create the GitHub API Integration

Before importing the repo you need a Git API integration in your Snowflake account. Run the following in a SQL Worksheet as **ACCOUNTADMIN**:

```sql
USE ROLE ACCOUNTADMIN;
CREATE API INTEGRATION IF NOT EXISTS GIT_HUB_INTEGRATION
  API_PROVIDER     = git_https_api
  API_ALLOWED_PREFIXES = ('https://github.com/')
  ENABLED          = TRUE;
```

This only needs to be done once per account. If your account already has a GitHub integration, skip this step.

---

### Step 2 — Import the repo into a Snowflake Git-backed Workspace

1. In Snowsight, open **Projects → Workspaces** and choose **New Workspace → From Git Repository**.
2. Paste the repo URL: `https://github.com/sfc-gh-timjones/dbt_full_demo`
3. Select the integration created in Step 1 and choose the `dev` branch.
4. Snowflake clones the repo into your workspace. You can now open and run the SQL scripts directly from the workspace file browser.

---

### Step 3 — Seed PROD with historical data (`01_historical_data_generation.sql`)

Open `01_historical_data_generation.sql` in a SQL Worksheet and run the entire script as **SYSADMIN**.

What it does:
- Creates `PROD_RAW_DB` and the `ORACLE` schema.
- Creates all source tables (PROV, VENDOR, etc.) with surrogate primary key columns matching the customer schema.
- Calls a stored procedure that generates synthetic provider and vendor data.

> `PRV_XREF` and `PRV_XREF1` are ~3.7 M rows each — allow a few minutes for those inserts to complete.

---

### Step 4 — Clone PROD into DEV and TEST (`02_clone_prod_raw.sql`)

Run as **SYSADMIN**.

Creates `DEV_RAW_DB` and `TEST_RAW_DB` and performs a schema-level clone of `PROD_RAW_DB.ORACLE` into each. The `PUBLIC` schema (where tasks and procedures live) is never touched — it stays empty in DEV and TEST.

---

### Step 5 — Create roles, databases, warehouses, and grants (`03_analytics_env_setup.sql`)

Run from an **ACCOUNTADMIN** session (the script switches roles internally as needed).

Creates:
- Roles: `DEV_ANALYTICS_RL`, `TEST_ANALYTICS_RL`, `PROD_ANALYTICS_RL`
- Databases: `DEV_ANALYTICS_DB`, `TEST_ANALYTICS_DB`, `PROD_ANALYTICS_DB`
- Warehouses: `DEV_ANALYTICS_WH`, `TEST_ANALYTICS_WH`, `PROD_ANALYTICS_WH`
- All USAGE, SELECT, and ownership grants

At the end of this script your current user is granted all three analytics roles.

---

### Step 6 — Set up the daily pipeline (`04_incremental_data.sql`)

Run as **SYSADMIN**.

Creates:
- `CHANGE_TRACKING` on `PROV` and `VENDOR` in all three raw databases
- `INSERT_INCREMENTAL_DATA()` procedure + `DAILY_DATA_INSERT` task (8am MT)
- `REFRESH_DEV_TEST_CLONES()` procedure + `DAILY_CLONE_REFRESH` task (child, fires after insert)

The script resumes the child task before the root task — this order is required by Snowflake.

To trigger the pipeline immediately without waiting for 8am:

```sql
EXECUTE TASK PROD_RAW_DB.PUBLIC.DAILY_DATA_INSERT;
```

---

### Step 7 — Run dbt

The dbt project lives in `dbt_template_example/`. Copy `profiles.yml` to `~/.dbt/profiles.yml` (or pass `--profiles-dir .`). Set environment variables before running:

| Variable | Description |
|---|---|
| `DBT_CURRENT_ROLE` | Snowflake role |
| `DBT_DATABASE` | Target analytics database |
| `DBT_WAREHOUSE` | Warehouse to use |
| `DBT_SOURCE_DB` | Raw database to read from |

**Dev**

```bash
export DBT_CURRENT_ROLE=DEV_ANALYTICS_RL
export DBT_DATABASE=DEV_ANALYTICS_DB
export DBT_WAREHOUSE=DEV_ANALYTICS_WH
export DBT_SOURCE_DB=DEV_RAW_DB

cd dbt_template_example
dbt run --full-refresh
```

**Test**

```bash
export DBT_CURRENT_ROLE=TEST_ANALYTICS_RL
export DBT_DATABASE=TEST_ANALYTICS_DB
export DBT_WAREHOUSE=TEST_ANALYTICS_WH
export DBT_SOURCE_DB=TEST_RAW_DB

dbt run --full-refresh
```

**Prod**

```bash
export DBT_CURRENT_ROLE=PROD_ANALYTICS_RL
export DBT_DATABASE=PROD_ANALYTICS_DB
export DBT_WAREHOUSE=PROD_ANALYTICS_WH
export DBT_SOURCE_DB=PROD_RAW_DB

dbt run
```

Always use `--full-refresh` on first run and after every re-clone. This rebuilds `dim_provider` from scratch and recreates `fct_provider_county_summary`'s change stream, which breaks when the source schema is replaced. Production uses plain `dbt run` (incremental) — rows on or after the current watermark merge safely without duplication.

## CI/CD (Future Phase)

Automating promotion from dev → test → prod via a CI/CD pipeline is the next phase of this pattern. The intended flow:

```
PR merged to main
        │
        ├──────────────────────────────────────────────┐
        │                                              │
        ▼                                              ▼
┌─ Test Run ──────────────────┐      ┌─ Prod Run ──────────────────┐
│  role: TEST_ANALYTICS_RL    │      │  role: PROD_ANALYTICS_RL    │
│  dbt run --full-refresh     │      │  dbt run                    │
└─────────────────────────────┘      └─────────────────────────────┘
        │                                              │
        ▼                                              ▼
  TEST_ANALYTICS_DB                           PROD_ANALYTICS_DB
```

Because `TEST_ANALYTICS_DB` and `PROD_ANALYTICS_DB` are owned by their respective roles (set in `03_analytics_env_setup.sql`), only the CI/CD service account — not individual developers — can write to those databases. Authentication via OIDC (no stored passwords).
